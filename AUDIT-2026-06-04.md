## 1. Persistance Supabase — interventions (task #257)

Le store `lib/maintenance-visits-store.ts` a maintenant trois chemins :

1. **Supabase** activé si `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` sont set
   → toutes les ops (`listVisits`, `getVisit`, `createVisit`, `updateVisit`, `deleteVisit`) passent par PostgREST
2. **Fichier local** sinon (dev)
3. **Mémoire** sur Vercel readonly (fallback transparent)

Le cache mémoire reste tenu à jour dans TOUS les modes — sert de filet contre les race conditions entre POST et GET sur cold-start Vercel.

**Migration SQL livrée** : `supabase/migrations/20260604_003_maintenance_visits.sql`
- Table `maintenance_visits` avec contraintes CHECK sur `type` et `status`
- 5 indexes (lead_reference, contract_id, visited_at, status, technician_email)
- Trigger `updated_at` réutilisé de la migration 001
- Notes opérationnelles sur la taille signature, l'absence de FK (RGPD), RLS

**Pour activer en prod** :
1. Exécuter la migration dans le SQL editor Supabase
2. Set `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` dans Vercel project settings → redeploy
3. Les nouvelles interventions persisteront durablement

Tant que les env vars ne sont pas set, le comportement actuel (mémoire Vercel + sessionStorage côté client) continue de marcher pour la démo.
